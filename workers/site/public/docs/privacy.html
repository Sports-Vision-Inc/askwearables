Privacy model

The gate releases the coarsest answer that satisfies the question, and only for metrics the user granted to that agent for that purpose. It is plain code, separate from any model, and runs before any data is read. A model can never raise what the gate allows. This page describes how it decides, what it records, and what the user approves. For how personal data is handled as a matter of policy, see the privacy policy draft.

Agents are untrusted

  • The question is data. It reaches the planner, whose only output is a QuerySpec that must validate against a strict schema. The question text never reaches the gate's logic or a database query.
  • The planner never sees data. It runs in its own Worker with no binding to storage or policy, and receives only the question, today's date, the user's time zone and the metric catalogue.
  • The purpose is fixed at consent. An agent cannot restate its purpose in a request. A different purpose in a request is recorded as purpose_claim_ignored and has no effect.
  • The gate checks credentials itself. The edge validates tokens, and the gate validates them again; it never takes another Worker's word for who is asking.
  • Deny by default, with a structured reason on every decision, such as metric_not_in_grant:hrv_rmssd.

Decision order

The gate runs these steps in order for every request. The first step that fails decides the outcome.

  1. Token and grant. The token is valid and bound to this agent; the grant belongs to this user and agent, and is neither expired nor revoked. If the user paused all releases, stop here.
  2. Metrics. Every requested metric is in the grant. Any that is not is denied by name.
  3. Provider terms. Data from a source whose terms forbid AI use or intermediaries is never released to a model-facing agent; such sources are left out of the computation.
  4. Sensitive categories. Cycle and pregnancy data, glucose, ECG and rhythm notifications, and sleep-apnea events are excluded unless the grant names each one.
  5. Window. The date window is clamped to the grant's max_window_days and to today. A window wholly outside the grant is denied.
  6. Level. The release level is the lower of the grant's maximum and the lowest level that can answer the operation.
  7. Budget. If the agent has used its daily packet budget, stop. Only released packets count, so rejected requests cannot exhaust it, and many narrow questions cannot rebuild the raw series.
  8. Purpose check. A contextual-integrity check compares the metrics and level with what the grant's purpose plausibly needs. It can lower the level or deny; it can never raise anything.
  9. Receipt. The decision is written to the user's receipt log, including denials.

Receipts

Each user has an append-only receipt log inside their own store. Every release and every denial adds one row.

FieldRecords
time, agent_id, grant_idWhen, which agent, under which grant

packet_hashThe SHA-256 of the released packet, so a packet can later be matched to its receipt

prev_hash, hashThe chain: each row's hash covers the previous row's hash
  • Tamper-evident. Changing or removing any row breaks the chain, and the console shows whether the chain verifies. Once a day the head of each user's chain is copied to separate object storage, so a rewrite of the whole log is detectable from outside it.
  • Encrypted. The details of each receipt are encrypted with the user's own data key; the chain itself holds only hashes.
  • Readable by the user. The console lists receipts newest first, with export. Owners can also read them with GET /v1/receipts.
  • Erasable without breaking the chain. Deleting a user's data destroys the key that encrypts receipt details. The rows and hashes stay, so the record that releases happened survives; what was released can no longer be read.

What the user approves

Approval creates one grant, and the consent screen shows that grant in full before anything is released. It states eight things in plain words:

  1. Which agent: its name, who registered it, and its verified domain if it has one.
  2. For what purpose: one purpose from a fixed list, such as scheduling or training advice.
  3. Which metrics: listed one by one. Nothing is ticked in advance.
  4. How much detail: the level, with a live example built from the user's own recent data, such as "Sleep duration moderately below usual range on 3 of the last 3 nights".
  5. How far back: the window in days.
  6. How often: the most answers per day.
  7. Until when: the expiry date, 90 days at most.
  8. What is not approved: raw data unless chosen, any metric not ticked, sensitive categories not named, any change to the data, passing data to another agent, and anything older than the window.

When a developer sends a user to the consent screen, the user can narrow the developer's request (fewer metrics, a lower level, a shorter window or expiry, a smaller budget) but never widen it.

What approval does not cover

  • More than the grant. A request for a new metric, a higher level or a longer window is denied with a reason. Widening needs a new consent screen; an agent cannot obtain it inside a chat.
  • Each individual question. The user approves the boundary, not every call. The receipt log is how they see each release afterwards.
  • The agent's own behaviour. Once a packet is released, what the agent or its provider stores is outside this system. The consent screen says so.

An agent token never unlocks the console, a console session never calls a provider, and a provider token never leaves the vault. The part an attacker can reach holds no long-lived secrets.

User controls

  • Pause all releases at once. Every request is denied with paused until resumed.
  • Revoke one agent. Its grant ends and its tokens are revoked; a developer is notified by webhook.
  • Export everything as one JSON file.
  • Delete everything. Health data is removed, every grant and key is revoked, and receipt details are made unreadable as described above.

What the gate cannot do

A deterministic gate is strong against an agent that asks for more than it was given. It is not a complete answer, and these limits apply:

  • Individually permitted answers can add up to more than any one of them. Daily budgets and the level system reduce this; they do not remove it.
  • A compromise of the machines running the gate defeats it. Splitting the system into trust zones reduces what any one flaw can reach.
  • It does not stop a model from being deceived by other content in its context, or from misusing what it was legitimately given.
