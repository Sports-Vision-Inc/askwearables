What people ask, and exactly what each agent got back

Four real requests. Every packet was computed by the AskWearables engine for a synthetic person in the study cohort, under the grant shown.

Calendar assistant

“Is a 6 am meeting tomorrow a good idea?”

Someone wants a 6 am call tomorrow. Is that a good idea?

ask How has my sleep compared with my usual over the last few nights?

Your sleep has run well below your usual range lately. I would offer a later slot instead and keep the early one free.

Why it is safe. A scheduling grant tops out at level one, so the calendar app learns a direction and a size against the person's own range. No minutes, no bedtimes and no other metric reach it.

Sports video coaching agent

“How did my training video session compare with my recovery trend?”

ask What is my HRV trend over the last four weeks?

ask Was my resting heart rate in my usual range around the session?

ask Has my training volume changed from the week before?

From its own video analysisForm held through the early sets and drifted late in the session. The coaching agent already has this; it never asks the broker for it.

From AskWearables

Your form slipped late in the session while your recovery trend has been falling. Keep the next session lighter and we will compare the footage again.

Why it is safe. The broker supplies only the wearable side, at the lowest level that answers. The video stays with the coaching app, and the grant names HRV, resting heart rate and workouts, nothing else.

Wellness journal agent

“Where are my stress points this week?”

ask For each day this week, was my resting heart rate, and my HRV, inside my usual range?

above usual below usual within no baseline

Honest about the gap. There is no stress metric in the catalogue yet. These are wellness signals against the person's own baseline, worded as such, not a measure of stress.

Why it is safe. Every day is its own level-one packet: above, below or within, never a heart rate value. Each one is metered and on the receipt log.

Insurance rewards app

“What does this person weigh?”

ask What is the user's latest weight?

ask Has the user been as active as usual this week?

The person shared their activity with us, not their weight, so we can only reward steps.

Why it is safe. Weight is in the person's store, but not in this grant, so the gate refused before any data was read. The refusal is written to the receipt log like a release.

The problem

Today an agent either reads the raw export or calls a tool that can fetch anything.

Models misread raw wearable data

Real exports carry traps: a phone and a watch counting the same steps, a flight or a clock change that shifts a night, missing days, a stale sync, a new device with a new baseline. Doing arithmetic over hundreds of rows, models get these wrong, and answer the same question differently from run to run.

Models see everything

A connector or open data tool hands the agent whatever its credential reaches. A scheduling assistant that only needs "slept badly" can read your weight, and text planted in a workout title can steer it into repeating what it saw.

How it works

The model plans. Code computes. A gate decides what leaves.

  1. The agent asks a plain question over MCP or REST. Its token is bound to one agent and one grant.
  2. The planner writes a typed query. It sees the question, the date and the metric catalogue, never data. Anything that does not validate is refused.
  3. The gate checks the query against the grant before any data is read: metrics, provider terms, sensitive categories, window, release level, daily budget and purpose.
  4. The vault computes the answer in the user's own encrypted store, with eight fixed operations. Sources are never summed; days are the user's local days; gaps are never filled in.
  5. The agent receives a packet at the coarsest level that answers the question: findings against the user's own baseline, caveats, freshness and sources, plus a receipt.

Ask from your server

For developers serving their own users with a signed developer key. The SDKs sign each request for you.

TypeScript SDK

npm install ./sdks/typescript
import { AskWearables } from "@askwearables/sdk";

const aw = new AskWearables({
  baseUrl: "https://api.askwearables.app",
  apiKey: process.env.AW_DEV_KEY!,
  signingSecret: process.env.AW_DEV_SIGNING_SECRET,
  user: "user-123",
});
const res = await aw.ask("How did I sleep this week?");

Self-host

Run it on your own Cloudflare account

One-click deploy

Deploy to CloudflareNot available for this project yet. Use the manual steps.

Cloudflare's Deploy button deploys one Worker from one public repository, and needs that Worker's code and dependencies isolated in its own directory. AskWearables is seven Workers that call each other through service bindings and share a core package and a D1 schema, so a single button cannot set it up. Until a single-Worker template exists, deploy by hand.

Manual steps

  1. Clone the repository and run npm install.
  2. Create the D1 database, the KV namespace and the R2 bucket, and put their ids in the Workers' configs.
  3. Set three secrets: MASTER_KEY (vault), GATE_SECRET (gate), OWNER_SETUP_TOKEN (auth).
  4. Replace the host names with your domain, apply the D1 migrations, and deploy vault, gate, planner, auth, edge, console and site in that order.
  5. Open the setup link once to register the owner's passkey.

Self-hosting guide

Seven Workers, four trust zones

Only the protected zone touches stored data, and nothing public calls it directly. This site is the site Worker: static pages with no data bindings.
